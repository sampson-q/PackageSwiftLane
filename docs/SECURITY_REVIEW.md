# Swiftlane security review and remediation register

Date: 29 October 2026. Branch: `secureswift`. Starting commit: `0d1eb1f6d89eda5100aadb9ac318892c46ebc860`.

## Executive assessment

**Security hardening is implemented, but production security sign-off is withheld.** The supplied checkout has no `loader.php`, private configuration, or representative application database. Consequently, the complete application, all role assignments, provider integrations and existing customer data could not be exercised. Encrypted/protected components also prevent a complete source review. This report does not claim that all vulnerabilities are eliminated, that every legitimate workflow is unchanged, or that ISO 27001 certification or a SOC 2 examination has been achieved.

The review used repository-wide security pattern searches, targeted source and authorization tracing, dependency version/advisory comparison, a limited secret-pattern/history scan, executable regression fixtures, and real Apache rule tests. PHP syntax validation does not constitute a complete semantic source audit. Security tests use disposable data; no production account was contacted, no payment or message was sent to an external recipient, and no production change or deployment was performed.

The implementation preserves the business calculations, shipping states, data schemas, report templates and existing file/link paths wherever addressed. It intentionally changes unsafe authorization and authentication behavior. Legitimate-workflow equivalence still requires the staging checks below.

## Validation evidence

Run from the repository root, after `composer install` with PHP, GD, mbstring, curl, XML and PDO SQLite available:

```sh
python3 scripts/security_checks.py
php tests/security/run.php
php tests/security/otp_checks.php
node tests/security/frontend_checks.js
python3 tests/security/http_checks.py
python3 tests/security/apache_checks.py
composer validate --no-check-publish
composer check-platform-reqs
node scripts/check_page_shell.js
```

The Apache test requires Apache 2.4 binaries/modules. `PHP_BINARY`, `APACHE_BINARY` and `APACHE_MODULE_DIR` may select local test tools. The fixture servers listen on loopback and stop after testing. SQLite fixtures validate actual authorization SQL and lifecycle behavior, but cannot establish MySQL row-lock concurrency, production schema compatibility or complete application behavior. Mail tests compose and queue messages with a fixture transport; they do not send mail.

The original `phpunit --do-not-cache-result` suite has **59 tests, 97 assertions and three pre-existing errors**, caused by the bootstrap missing the shipment formatter's `cdp_getEffectiveStatus()` helper. Those failures remain visible; tests/assertions were not disabled or replaced to produce a green full-suite result. PHPUnit and ClickSend also report compatibility deprecations under PHP 8.4. Consult the final validation record in `SECURITY_VALIDATION.json`.

The live Packagist advisory request was blocked by the environment's network policy. An official FriendsOfPHP advisory snapshot at commit `64403e9edb1344e646bf35cebde20e0f18632441` was evaluated with Composer Semver: **17 old package/version–advisory range matches, zero matches for the new root lock in that snapshot**. This is not a clean live audit or proof of absence of undisclosed issues. Detailed matches and lock hash are in `SECURITY_DEPENDENCY_EVIDENCE.json`.

The limited high-confidence credential-pattern scan of the working tree and 1,251 reachable commits found the old public TCPDF example private key, now removed from the working tree. It did not establish that all historic credentials are absent. History was not rewritten, and real credentials were not rotated or printed.

## Required deployment actions and behavior changes

1. Obtain a matching non-production loader, private configuration, full schema and representative fixtures. Run all role/workflow tests before release. Do not deploy this branch solely because fixture tests pass.
2. Review the actual role/grant/department/agency/branch matrix. Previously bypassed permission denials now return 403 for every role. Correct intended grants and account metadata with the business owner; do not restore the audit/off bypass. Unknown role types fail closed.
3. Configure a stable, random `CDP_AUTH_SECRET` of at least 32 characters through private configuration or a server-side secret manager that provides the actual key bytes. An outbound proxy credential placeholder is not a cryptographic key. A confidential database password of at least 12 characters is the compatibility fallback; public database names are no longer accepted as key material. Share the same secret across application nodes. Do not put the value in Git, logs, tickets or chat.
4. After the normal API/OTP tables exist, back up the database and apply `api/v1/migrations/002_security_token_revocation.sql` during maintenance. All four tables must exist. Its statements intentionally invalidate existing credentials. Existing browser sessions also reauthenticate because credential-version metadata is new; old trusted devices/OTP codes reset when key derivation changes.
5. API clients must support a 202 `otp_required` response with `challenge_id`; resubmit the same credentials with that ID and the delivered six-digit `otp_code`. When the configured OTP policy is off, the normal token response remains. Test correct/incorrect/expired/replayed codes and inactive accounts. Machine credentials do not receive an implicit MFA exemption.
6. Provision the pinned root Composer dependencies in deployments (`composer install --no-dev --prefer-dist --no-interaction --no-scripts --no-plugins`). Old `helpers/vendor/autoload.php`, PHPMailer and PDF include paths are compatibility facades, not independent package installations.
7. Require HTTPS at the ingress, configure HSTS after validating the domain/TLS rollout, and correctly set trusted proxy/peer addresses. Cookies are Secure by default even behind TLS termination. `CDP_SESSION_COOKIE_SECURE=false` is for an explicitly isolated local HTTP development instance only; never use it in production.
8. Apache needs `mod_rewrite`, `mod_headers` and authorization support with these directory overrides enabled. Mirror the restrictions in nginx/IIS. PHP-FPM/CGI can use `.user.ini`; mod_php needs equivalent administrator configuration. Confirm actual HTTP denial of hidden files, backups, tests, internal code and executable upload names.
9. Make `CDP_SECURITY_STATE_DIR` a private, writable directory outside the document root (0700), backed by persistent storage when appropriate. File-backed limits are single-node controls. For multiple replicas, add a shared limiter at the ingress/service layer. Tune NAT/proxy handling and monitor storage capacity; never trust arbitrary client-supplied forwarding headers.
10. Test allowed upload types, multiple files, videos, logo/profile images, printing, CSV/Excel import, shipping state changes, billing, gateway callbacks and external providers using sandbox accounts. Restore valid CA chains where old integrations depended on disabled TLS verification. No live provider or payment tests were performed here.
11. Take an application/database backup and keep a reviewed rollback release. Rotate/revoke credentials as planned; rolling back code does not safely restore old authentication tokens. Preserve denial/audit records and compare key workflows before reopening access.

## SOC monitoring handoff

Collect `api_denied`, `object_access_denied`, AJAX permission denials, failed logins, OTP lockouts and changes to roles/security settings in a centrally restricted log destination. Alert on repeated denials across many records/accounts, unusual privileged impersonation, bulk exports, backup downloads/deletions and unexpected token issuance. Investigate before increasing limits. Never ingest raw passwords, Bearer/refresh/reset tokens, OTP codes, cookies or provider keys.

Assign incident ownership, revoke affected tokens/devices when appropriate, preserve sanitized evidence, verify account/role integrity, and record containment/recovery decisions. Establish retention, clock synchronization, review frequency, remediation deadlines and periodic backup-restore tests with the organization's actual risk owners. These operational processes have not been executed or attested by this code change.
